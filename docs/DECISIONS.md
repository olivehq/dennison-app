# Decisions

Decisions made while building, where the source documents were silent or ambiguous. Each one can be reversed by D&A before engine sign-off. Dates are 2026.

| # | Date | Decision | Why |
|---|---|---|---|
| D1 | Oct 4 | Biztech opt-in: a participant is opted in when they appear with at least one choice in the biztech ranking file. Opted-out participants are never matched with business suppliers. Admins can flip the flag per participant. | The SOW names the rule but does not define it. The three-file import makes the biztech file the natural signal. |
| D2 | Oct 4 | In the eShow `CHOICE #n` list format, a supplier missing from a row is unranked, not rejected. Rejection (`is_rejection`) only comes from an explicit `N/A` in the 2025 matrix format or from an admin marking it in the app. | The list format has no way to say never. Treating omission as rejection would make most pairs ineligible. |
| D3 | Oct 4 | Ranking files are matched to people by `FULL_NAME` through the alias table when they carry no email. The participants file is the only place email is required. | The sample eShow export has no email column. |
| D4 | Oct 4 | Supplier type (business or hotel) comes from a `type` column in the suppliers template. Admins can change it in the app. | Nothing in the source files classifies suppliers. |
| D5 | Oct 4 | Light theme by default, dark toggle available. | Staff use the app on a bright show floor. |
| D6 | Oct 4 | One Postgres driver, postgres.js, for Neon and local Docker. PGlite for tests and for local dev when `DATABASE_URL` is unset. | Keeps one code path in production while letting tests run with no services. |
| D7 | Oct 4 | File storage goes through a tiny adapter: Vercel Blob when `BLOB_READ_WRITE_TOKEN` is set, otherwise the local `.data/uploads` folder. | Lets the app run locally without a Vercel account. |
| D8 | Oct 4 | Email goes through an adapter: Resend when `RESEND_API_KEY` is set, otherwise a logger that prints the message. | Same reason as D7, and it keeps tests from sending mail. |
| D9 | Oct 4 | The engine ships as `src/engine` inside the app, not a workspace package. A lint rule forbids it from importing Next.js or the database. | One app is simpler than a monorepo. The lint rule keeps the engine pure. |
| D10 | Oct 4 | Pinned appointments survive a re-run. "Re-run and keep existing" pins every appointment that does not involve a withdrawn person. | Required so late changes do not throw away manual edits. |
| D11 | Oct 4 | Optimistic concurrency uses a `version` column on `match_runs`. Every schedule save sends the version it read. | Cheapest way to stop two admins overwriting each other. |
| D12 | Oct 4 | One `audit_events` table for every change, with before and after JSON. Undo replays `before`. | One log is easier to read and query than several. |
| D13 | Oct 4 | A person has "changed since last send" when the hash of their current schedule differs from the hash stored on their most recent delivered email. | Lets update emails go only to affected people. |
| D14 | Oct 4 | Participant tokens: 32 random bytes, base64url in the link, SHA-256 in the database. Default expiry 60 days after the event date. | Standard unguessable link pattern, no accounts. |
| D15 | Oct 4 | All admins have equal access. No roles. Disabling an admin ends their sessions. The last active admin cannot be disabled. | The SOW has one kind of user. |
| D16 | Oct 4 | Slot times are stored as minutes from midnight in the event timezone, with a per-slot start and end. Display always uses the event timezone. | Avoids date-time bugs when staff travel. |
| D17 | Oct 4 | Desk numbers are assigned alphabetically by supplier name at lock time. Suppliers with a manual override keep their number. | SOW 2.5. |
| D18 | Oct 4 | The 2025 matrix format is supported by the importer in addition to the eShow list format. | D&A still has the 2025 files in that shape and the engine regression needs them. |
| D19 | Oct 4 | Event settings live in a jsonb `settings` column on `events`, validated by `eventSettingsSchema` on every write, instead of a separate `event_settings` table. | One row per event either way; a column avoids a join and a second insert on create. The zod schema is the contract. |
| D20 | Oct 4 | Better Auth's `user` model is the `admins` table. Drizzle property names stay camelCase to match the adapter (`emailVerified`, `userId`), SQL names are snake_case. Extra columns `disabled_at` and `invited_by`. | The scope calls the table `admins` and the app has one kind of user. Better Auth only cares about the schema keys passed to the adapter. |
| D21 | Oct 4 | Better Auth's rate limiter uses `storage: "database"` with a `rate_limits` table. Login, sign-up, and password reset requests are capped at 5 per 10 minutes per IP. | The default in-memory store resets on every serverless cold start, so it would not limit anything on Vercel. |
| D22 | Oct 4 | Disabling an admin deletes their `sessions` rows directly in the same transaction and sets `disabled_at`. New sign-ins are refused by a `session.create.before` hook. No Better Auth admin plugin. | The admin plugin brings roles and bans we do not want (D15). Deleting the rows is the same effect with no extra concepts. |
| D23 | Oct 4 | `audit_events.created_at` defaults to `clock_timestamp()`, not `now()`. | Postgres freezes `now()` for a whole transaction, so several audit rows written in one save would tie and the activity log could not order them. |
| D24 | Oct 4 | Sign-up is only possible through an invite link. `databaseHooks.user.create.before` rejects any email without a pending, unexpired `admin_invites` row and `.after` marks the invite accepted. Invite tokens: 32 random bytes, base64url in the link, SHA-256 in the database, 7-day expiry. | Scope says no self-signup and a team page with invites. Doing it in the hook means the rule holds for every sign-up path, not just our form. |
| D25 | Oct 4 | `import_kind` includes `suppliers` alongside the four files named in the scope. | D4 says supplier type comes from a suppliers template, which implies a fifth upload. Adding the enum value now is free; adding it later is a migration. |
| D26 | Oct 4 | Local dev with no `DATABASE_URL` opens PGlite at `.data/pglite`. Only one process can hold that directory, so stop `pnpm dev` before `pnpm db:migrate` or `pnpm db:seed`. | PGlite is single-connection by design. Tests use in-memory instances and are unaffected. |
| D27 | Oct 4 | `assertEventEditable` lives in `src/server/events/editable.ts`, not in `actions.ts`. Each module's actions file stays a thin `'use server'` wrapper over a plain module that takes the `db` handle. | A `'use server'` file may only export async functions, and plain modules can be tested with `createTestDb()` without a request context. |
| D28 | Oct 4 | The first admin is created by `pnpm create-admin`, which writes the `admins` row and a credential `accounts` row (password hashed with Better Auth's `hashPassword`) directly. Every later admin comes through an invite. | Invites need an inviting admin, so the first account cannot go through the invite hook. |
| D29 | Oct 4 | The settings page saves in two calls: `updateEvent` for name, date, and timezone, `updateEventSettings` for the settings JSON, and only the sections the user changed. Slot count is derived from the slot table; "Rebuild slots" fills the table from count, first start, duration, and gap. | Two audit rows with clear before and after beats one mixed row, and nothing is written when nothing changed. |
| D30 | Oct 4 | The timezone picker lists `Intl.supportedValuesOf('timeZone')` from the browser. Node's list has no plain `UTC`; use `Etc/GMT` or a city. | No bundled timezone table to keep current. The schema checks the same list on the server. |
| D31 | Oct 4 | The database holds only token hashes (D14), so any feature that needs plain links again must rotate them. `issueAccessList` (the access CSV) revokes every live token of the event and issues new ones; email sends will do the same per recipient. The newest link always works; links handed out earlier stop. Superseded Oct 4 by D59: tokens are also stored encrypted, so `issueAccessList` and email sends reuse each contact's current link and only issue for contacts with none. Nothing rotates any more; a token from before D59 (no ciphertext) is revoked and replaced the first time it is needed. | The alternative is storing plain or reversible tokens, which D14 ruled out until D59. |
| D32 | Oct 4 | Undo replays `before` through the normal edit functions (`replaceAppointment`, `addAppointment`, `removeAppointment`), so the version check, eligibility, and hard rules apply. The log row is `appointment.undo` with the appointment snapshots in `before` and `after` and `note` = "Undo of audit event <id>". An undo can itself be undone; a change already undone is refused. | One write path for every schedule change. The note is how "already undone" is detected without a new column. |
| D33 | Oct 4 | Manual edits are allowed on any completed run; undo only on the active run. Lock needs an active run, not a particular status. Unlock is allowed from `locked` and `sent` and returns the event to `matched`. Pin and unpin also bump `match_runs.version`. Amended Oct 4 by D86: replace, add, remove, pin, and undo work only on the active run; anything else is refused with "This schedule is no longer the active one. Reload to see the current schedule." | Admins may want to touch up a run before activating it. After a send, the scope's "send update to affected people" flow needs the editor back. Any change to the run's rows must invalidate other admins' versions (D11). |
| D34 | Oct 4 | Buyer display name everywhere (warnings, views, exports): `display_name` when an admin set one, else "Organization - Title" when both exist, else first and last name. Suppliers show their name as is. Engine warnings are stored with ids already replaced by these names. | The 2025 files identified buyers by organization and title. Storing readable warnings means every reader of `match_runs.warnings` gets the same text. |
| D35 | Oct 4 | The matching, schedule, and tokens modules use a local `assertEditable(event)` in `src/server/matching/common.ts` that fails with code `locked` for `locked`, `sent`, and `archived`. Resolved Oct 4: matching uses `assertEventEditable` (D27) and the local copy is gone. `matching/common.ts` keeps `assertEditable` only as a deprecated re-export of the same function, because `src/server/schedule` still imports that name; drop it when schedule switches. Fully resolved Oct 4: `src/server/schedule` imports `assertEventEditable` and the alias is deleted. | The two modules were built in parallel without a shared file to import from. |
| D36 | Oct 4 | Import state shown to admins (`failed`, `needs_mapping`, `needs_fixes`, `ready`, `applied`) is derived from `imports.status` plus the validation report, not stored. `needs_mapping` means unknown names exist; `needs_fixes` means row errors (duplicate emails, missing emails, bad cells) with no unknown names. The `import_status` enum is unchanged. | The enum has `validated`, which covers both; adding values would be a migration in a shared file while three modules were being built in parallel. Deriving keeps one source of truth. |
| D37 | Oct 4 | A ranking row whose ranker is not on the roster and who ranked nobody is a warning and is skipped. A ranker with choices who is not on the roster blocks the import until mapped. | The eShow sample contains a "Jamie Test" row with no choices. Blocking on it would stall every real import. |
| D38 | Oct 4 | In the list format the rank is the `CHOICE #n` column number, not the position among filled cells. In the matrix a blank cell writes no `rankings` row; only a rank or an `N/A` does (D2). Names that resolve only through normalisation (case, punctuation, "the", "&" vs "and") are saved as `auto` aliases when the import is applied. | The column number is what eShow means by the rank. Auto aliases make the next year's file hit the exact path and show the admin what was assumed. |
| D39 | Oct 4 | Applying a ranking import deletes the rankings of every previously applied import of the same kind for the event, then writes the new rows (upsert on the pair key). Deleting an import also deletes the rankings it wrote. A file the parser cannot use at all (unreadable, no recognised columns, unknown ranking layout) is stored as a `failed` import with the message in the report. | Re-import replaces the file's rankings (scope 2.3). Orphaned rankings with a null `import_id` would otherwise collide with the next import. |
| D40 | Oct 4 | Roster and import writes use a local `assertEditable(event)` in `src/server/roster/editable.ts` (fails with `locked` for `locked`, `sent`, `archived`). Participants files are keyed by lower-cased email, suppliers files by case-insensitive name; neither touches `status`, so withdrawn people stay withdrawn. A blank Biztech opt-in cell keeps the current value. A desk number already held by another active supplier is refused. Resolved Oct 4: `loadEditableEvent` in `roster/editable.ts` now calls `assertEventEditable` (D27); the local helper is deleted. | Built in parallel with the events module. The identity rules follow D3 and D4. |
| D41 | Oct 4 | Each export download writes an `audit_events` row `export.<kind>` (`master`, `schedules`, `report`, `access_list`) with the admin, `entity_id` = run id, and `after` = `{ runId, runVersion }`. The exports page reads the newest row per kind for "Generated ... by ..." and shows "Schedule changed since this export" when the active run id or version differs. The access list never shows that warning; its links do not depend on the schedule. | One log (D12) already records who did what; a separate exports table would duplicate it. |
| D42 | Oct 4 | Export CSVs start with a UTF-8 byte order mark. Schedule file names follow the spec (`/` and `\` to `_`, `:` to `-`, no commas, 80 characters with `.csv`) and also turn `* ? " < > \|` into `_`; duplicates get `_2`, `_3`, compared case-insensitively. Withdrawn people get no file in the ZIP. Before lock, when suppliers have no desk, the desk column shows the supplier name alone. | D&A opens the files in Excel, which misreads UTF-8 without a BOM. 2025 buyer names contain `\|`, which Windows refuses when extracting. macOS and Windows file systems ignore case. |
| D43 | Oct 4 | Exports are Route Handlers under `/api/exports/[eventId]/` (master, schedules, report as GET; access as POST only). They answer 401 without a session, 404 for an unknown event, 409 with no active run, and 409 for the access list until the event is locked, sent, or archived. The access list POST also refuses a cross-origin `Origin`. The page fetches it behind a confirm and saves the blob, so a refusal shows as a toast and the page refreshes afterwards. The ZIP is streamed from archiver. | The access list rotates every link (D31), so it must not be a GET a prefetch or crawler could trigger. |
| D44 | Oct 4 | `/s/[token]` is `force-dynamic` and relies on Next's header for dynamic pages, `private, no-cache, no-store, max-age=0, must-revalidate` in production (verified with `next start`; `next dev` sends `no-cache, must-revalidate`). Metadata sets `noindex, nofollow` and `referrer: no-referrer`. Unknown, revoked, and expired tokens and withdrawn people all get the same "This link is not valid" page, rendered inline with status 200. | No config change needed for no-store. The referrer policy keeps the token out of any third-party request. One message for every failure reveals nothing about a link. |
| D45 | Oct 4 | `pnpm db:seed` builds "AW 2025 Appointment Show" from `fixtures/aw-2025-results.js` (parsed as JSON, never evaluated). Buyers get made-up names picked from a hash of their 2025 name and `first.last@example.org` addresses; supplier contacts are `<slug>@example.com` and `attendee.<slug>@example.com`. Every matched pair keeps its 2025 ranks; the 17 pairs a buyer left blank stay unranked. Every other pair gets the ranker's unused numbers shuffled by mulberry32 with a fixed seed. Buyers rank business and hotel suppliers as two lists, as in 2025. Each supplier's pool is 1 to max(65, its highest real rank), since 2025 supplier ranks go up to 72. The 2025 desks are written without override (desks superseded by D66), and the schedule goes in as a completed, active run (source engine) with stats from `computeStats`. | Swap candidates and re-runs need every pair ranked, and the demo must be identical on every run. |
| D46 | Oct 4 | Event status moves forward through `advanceStatus(tx, eventId, from, to)` in `src/server/events/status.ts`, a single compare-and-set UPDATE that only fires when the current status is one of `from`. Applying any import moves a `draft` event to `imported` in the same transaction; the import's audit row records `eventAdvanced`. | A conditional update can never move an event backwards (a matched event re-importing stays matched) and needs no read-then-write. |
| D47 | Oct 4 | Saving a supplier from the app also saves its desk: `upsertSupplier` leaves the desk alone when `deskNumber` is omitted or equals the current number (so a desk assigned at lock keeps `deskOverride` false), treats any other number as a manual override (D17), and clears it on null. A desk held by another active supplier is a `conflict` on `deskNumber`. | One dialog, one call, one audit row, and editing a contact can't silently turn a lock-time desk into an override. |
| D48 | Oct 4 | "Save all suggested" calls `saveAliases`, which writes every mapping in one transaction (all or nothing) and re-validates pending imports once. Applying a participants or suppliers import also re-validates every pending ranking import, so a file stuck on "Needs mapping" becomes "Ready" once the missing people are on the roster. Single roster edits in the app do not re-validate; upload the file again or save an alias. | Re-validating per alias would re-parse every pending file N times. Without the roster-apply re-check, adding missing suppliers left the ranking file blocked until it was uploaded again. |
| D49 | Oct 4 | `experimental.serverActions.bodySizeLimit` is `6mb` so `uploadImport` can take the 5 MB files it promises (`IMPORT_MAX_FILE_BYTES`) plus multipart overhead. The upload card also checks the size before sending. | Next's default 1 MB limit would reject a 2 MB file with a framework error instead of our message. Scope 2.3 says to move to Blob client uploads only if real files get near the limit. |
| D50 | Oct 4 | The roster pages show one link status per contact from its newest token: "Link active", "Revoked", "Expired", or "No link" when none was ever issued. Regenerate and revoke act on that newest token; a contact with no token has no link actions, because links are issued at lock (2.6). Suppliers show a badge per contact with an email. | The database keeps every rotated token (D31), so only the newest one says anything about today's link. |
| D51 | Oct 4 | Roster filters (status, biztech, type) live in the URL query and are synced with `history.replaceState`; search stays local. The "Changed since last email" column is left out with a TODO until the email module provides `recipientsChangedSinceLastSend`. Resolved Oct 4: the column shows "Changed", "Up to date", or nothing before a person was ever emailed, from `getScheduleChangeState` (D61). A supplier is "Changed" when either contact is. | Scope section 3 puts view state in the URL. A column with no data behind it would read as "nobody changed". |
| D52 | Oct 4 | Schedule workspace: `view`, `q`, `free`, and `sel` live in the URL and are written with `history.pushState` (view, slot filter, selected person) or `replaceState` (search typing), which Next.js syncs into `useSearchParams` without a server round trip. Edit mode, "count problems only", the by-slot pick, and the show clock stay local. | Links reproduce the screen and Back closes the sheet, without a server render per keystroke. |
| D53 | Oct 4 | The buyer distribution on the Quality view is drawn with plain bars, not shadcn Chart. | shadcn Chart needs Recharts, which is not installed, and the brief allows no new dependencies. Twelve bars do not justify one. |
| D54 | Oct 4 | Match strength treatment: mutual is a solid fill with the two-way arrow; one side is a tint with the edge bar on the side that ranked top N (left for the buyer, right for the supplier, the same order as the B and S badges); neither is an outline; a blank rank is a dashed outline. Pinned and hand-placed meetings carry a pin and a pencil icon. | The mockup has one "one side" treatment; the data distinguishes buyer-only from supplier-only and staff asked which side wanted it. |
| D55 | Oct 4 | Clicking a block selects the lane's person (the supplier in desk lanes, the buyer in buyer lanes) focused on that slot; the sheet row has "Open buyer" or "Open supplier" for the other side. In edit mode an open slot in a supplier lane opens the swap picker straight away; buyer lanes have no "add" because swap candidates are buyers for a supplier slot. | One sheet shape for every selection, and Replace always acts on a supplier slot, which is what the edit actions take. |
| D56 | Oct 4 | The show clock starts at the live time in the event timezone when the server's request date in that timezone equals `event_date`, else at the first slot. It ticks every 15 seconds while live; dragging, the arrow keys, the slot buttons, or Play leave live mode. Play advances one minute every 320 ms, or one slot every 1.5 s under `prefers-reduced-motion`. Fade finished is one veil over the finished minutes, not a per-block style. | The server decides "today" so the first render matches on both sides. A single veil keeps the 500-block lanes memoised while the line moves. |
| D57 | Oct 4 | `VERSION_CONFLICT_MESSAGE` moved to `src/lib/schemas/schedule.ts` (re-exported from `schedule/edits.ts`). The client toasts every failed edit; it also refreshes on the version conflict and on `locked`. | The client has to recognise the stale-version case without importing a server module. |
| D58 | Oct 4 | The matching page compares a run with the active run through `?compare=<runId>`, rendered on the server with `compareWithActiveRun` (new in `matching/queries.ts`, beside `getMatchingReadiness`). Lists show the first 40 rows each with "and N more". | No action needed for a read, the expansion is a shareable link, and a full re-run can differ in hundreds of rows. |
| D59 | Oct 4 | `access_tokens.token_ciphertext` holds the plain token encrypted with AES-256-GCM under a key derived from `TOKEN_PEPPER` (HKDF-SHA256), stored as base64 `iv.ciphertext.tag` (`encryptToken`/`decryptToken` in `src/lib/tokens.ts`). Every issue path stores it; `verifyToken` still looks up by hash. `linksForContacts` in the tokens module returns each contact's newest active link, issuing one only where none can be decrypted. | A reminder or update email must not kill the link in the first email, and the access list must print the links people already have. A leaked database without the pepper still yields no working links. |
| D60 | Oct 4 | `email_messages` stores `contact_type`, `entity_id`, and `recipient_name` beside `access_token_id`. `email_campaigns.selected_token_ids` is replaced by `selected_recipients`, a list of keys like `buyer:<id>` and `supplier_admin:<id>`. Campaigns get a `status` (`draft`, `sending`, `sent`, `failed`); only drafts can be edited or sent, and a send claims the draft with a compare-and-set to `sending` so a double click can't send twice. | Tokens can be regenerated or revoked, so the token is not a stable identity for "who was emailed". A contact selected before lock has no token yet. |
| D61 | Oct 4 | "Changed since last email" (D13) is per contact (a buyer, a supplier admin, a supplier attendee). The baseline is the contact's newest message with status `sent`, `delivered`, or `complained`; `bounced` and `failed` messages never reached the person and don't count. The hash is SHA-256 over every slot's number, start, end, counterpart id, and desk, OPEN slots included. People never emailed are not "changed"; withdrawn people and contacts without an email are left out of the count, so the count equals the update audience. | Times are on the participant page too, so a time change is a change. Counting people never emailed would send an "updated schedule" email to someone who never got the first one; use a selected audience for late additions. |
| D62 | Oct 4 | Webhook signatures are verified with `resend.webhooks.verify` from the installed `resend` package (it bundles `standardwebhooks`), wrapped as `verifyWebhook` in the email adapter. No `svix` dependency. Missing or bad signature: 401. No `RESEND_WEBHOOK_SECRET`: 200 and skip with a warning outside production, 500 in production. | Same verifier Resend documents, no new package, and the adapter stays the only file that touches Resend. |
| D63 | Oct 4 | Each sent message carries a Resend tag `aw_message=<email_messages.id>`. The webhook finds the message by provider id or by that tag, appends the event to `events` with the webhook id, and skips an event whose id is already there. Status only moves forward (queued, sent, delivered, then bounced, complained, or failed); `delivery_delayed`, `opened`, and `clicked` are logged without a status change; `suppressed` counts as bounced. Sends go in chunks of 100; a chunk Resend refuses marks only its messages `failed`. "Resend to bounced" retries recipients whose newest message in the campaign bounced or failed, at their current address. | A fast webhook can arrive before the batch response is saved; the tag closes that gap. Resend retries webhooks, so recording must be idempotent. |
| D64 | Oct 4 | The campaign preview renders on the server for one chosen recipient (`previewCampaign`, called as the editor changes, debounced) and is shown in a plain div after the browser's DOMParser strips everything but formatting tags and http, https, and mailto links. Preview links are not clickable. New campaigns copy sender and reply-to from the event's newest campaign, else `EMAIL_FROM` and the admin's own address. | No iframe and no sanitizer dependency. Opening a participant's link from the preview would record a view on their behalf. |
| D65 | Oct 4 | Participant links expire at the later of the end of the day 60 days after the event (event timezone) and 60 days after the moment they are issued. Amends D14. | A link issued or regenerated after the event date, such as a late resend or the demo event, used to be born expired. |
| D66 | Oct 4 | One name order everywhere names are listed or numbered: `compareNames` in `src/lib/names.ts`, an `Intl.Collator('en', { sensitivity: 'base', numeric: true })` with a code-point tie-break. Lock, the roster lists, exports, swap candidates, run comparison, and the import suggestions use it. The seed numbers desks with `planDesks` from lock instead of copying the 2025 sheet, so the demo's desks are the lock order ("eShow" is desk 7, not 56; "SEAS Productions" follows "Santa Maria"). Supersedes the desk part of D45. | The 2025 sheet sorted by code point, the lock sorted case-insensitively, so locking the seeded event renumbered desks. Numeric order keeps "Hall 2" before "Hall 10". |
| D67 | Oct 4 | A pin belongs to the slot: `replaceAppointment` gives the replacement row the old row's `pinned` and records `pinKept: true` in the audit `after`; undoing a removal puts a pinned appointment back pinned. `setPinned` takes the version the client read (optional) and bumps `match_runs.version` with a compare-and-set on the version it read, returning the version conflict when another save got there first. | Replacing a pinned meeting silently unpinned the slot, so the next "re-run and keep existing" could move it. Pins are saves too (D11, D33). |
| D68 | Oct 4 | Activity page (`/events/[id]/activity`): person, admin, type of change, and a from/to date range live in the URL; 50 rows a page, newest first. Types: schedule edits (`appointment.*`, desk reassignment), roster (participants, suppliers, links), imports (imports, aliases), matching, lock and unlock, emails, exports; `event.*` rows show under "All changes" only. The person filter matches the row's entity or a `buyerId`, `supplierId`, or `entityId` in before or after. Dates are whole days in the event timezone. Undo shows on replace, add, remove, and undo rows; it is disabled with the reason when the event is locked or archived, the row's run is not the active run, or a later undo names it (D32). Pin and unpin have no undo button; pin again from the sheet. Sentences come from `describeAudit` and name people with D34 names; people deleted since show as "a buyer" or "a supplier". | Scope 2.5 asks for filters by person, admin, and type. The URL makes a filtered log shareable, and the undo rules are the ones `undoAudit` already enforces, shown before the click. |
| D69 | Oct 4 | Retention (SOW 4): a Vercel Cron calls `GET /api/cron/retention` daily at 09:00 UTC with `Authorization: Bearer $CRON_SECRET` (401 otherwise, 503 when the secret is unset). Once the 90th day after the event has ended in the event timezone, and `settings.retainData` is not true, one transaction deletes the event's email messages, access tokens, appointments, match runs (their warnings hold names), rankings, name aliases, imports, participants, and suppliers, clears `before`, `after`, and `note` on its non-`event.*` audit rows, sets the status `archived`, and writes one `event.retention_delete` row with the counts and no admin. Stored import files are deleted after the commit; a file that fails is reported in the response, not retried. The event row, its settings, email campaign templates, and the log's who, what, and when stay. An archived event with nothing left is skipped, so later runs write nothing. | The SOW promises deletion or return within 90 days unless D&A asks in writing. Audit rows held names and emails in their snapshots, so keeping them intact would keep the data. |
| D70 | Oct 4 | "Keep participant data after 90 days" is `settings.retainData` (optional, missing means false), set only through `setRetainData`, which works in every status except archived and writes an `event.retention` audit row. `updateEventSettings` keeps the stored value whatever the form sends.
